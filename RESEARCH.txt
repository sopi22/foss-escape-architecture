2. NOVELTY FIREWALL (Section 4)
================================================================================

Applied to the project as a whole, before any implementation.

Existing systems checked:

1. Android Compatibility Test Suite (CTS) / Google's Compatibility
   Definition Document (CDD).
   What it solves: OEM/vendor-level certification that a device's OS build
   conforms to the Android platform spec. Run by manufacturers, not app
   developers, against a fixed suite defined by Google.
   Residual gap: CTS certifies the OS build once, at the vendor level. It
   does not track app/assumption-level behavioral drift over time on a
   specific device a developer actually has in hand, and it has no notion
   of a developer-authored, falsifiable "operating assumption" with a
   PASS/FAIL/UNKNOWN outcome comparable run-over-run.

2. `adb shell dumpsys` / `getprop` / `pm` metadata inspection (the
   conventional baseline this experiment compares against).
   What it solves: fast, cheap inspection of declared device/OS state
   (API level, declared features, granted permissions as recorded by the
   OS).
   Residual gap: this is exactly declared/metadata state, which H1 predicts
   is sometimes insufficient — e.g. OEM policy layers can silently override
   or diverge from what metadata claims. Metadata inspection cannot, by
   construction, detect that divergence; only an actual behavioral probe
   can. This is the core residual gap the experiment targets.

3. Device farms / compatibility matrices (Firebase Test Lab, BrowserStack,
   etc.).
   What they solve: running an app's own test suite across many real
   device/OS combinations, hosted externally.
   Residual gap: these are external, network-dependent services (violates
   the entropy budget's "external services: 0" and "network calls: 0"
   directly), oriented around a specific app's test suite rather than a
   portable, comparison-over-time assumption ledger, and don't produce the
   FACT/HYPOTHESIS/DECISION epistemic trail this experiment requires.

4. Espresso / UI Automator / Robolectric / Monkey.
   What they solve: UI-behavior correctness testing and fuzz/stress testing
   of a specific app.
   Residual gap: oriented at app-internal UI correctness, not at
   standalone, per-assumption environment-compatibility probing that can
   run without any app installed.

5. Play Integrity API / SafetyNet attestation.
   What it solves: device/app integrity attestation for anti-abuse
   purposes.
   Residual gap: itself a declared/opaque verdict from a remote service —
   exactly the kind of "advertised capability treated as evidence" H1's
   epistemic rules explicitly reject as a substitute for direct behavioral
   observation. Also an external network service, out of budget.

CONCLUSION: no existing system combines (a) developer-defined, falsifiable,
per-assumption behavioral probes, (b) explicit run-over-run comparison state
(NEW/UNCHANGED/CHANGED/NO_COMPARISON) as a first-class output, and (c)
explicit epistemic logging that refuses to treat declared/metadata state as
evidence of actual behavior. Integrating an existing tool would not close
this gap — building the minimal probe harness is justified.

Re-applied at probe-selection level below, per-probe, where a candidate
probe resembled an existing solved problem (background-service liveness,
network cleartext policy, package-visibility API changes).

3. RESEARCH HYPOTHESIS FRAMING (Section 5)
================================================================================

RESEARCH HYPOTHESIS (H1):
A meaningful subset of software/environment compatibility failures can be
represented as explicit, falsifiable operating assumptions whose state is
observable through safe behavioral probes and comparable over time.

NULL HYPOTHESIS (H0):
Behavioral probing provides no materially useful information beyond
conventional environment metadata for the compatibility failures tested.

FALSIFICATION CRITERIA:
If, across the selected probes, the behavioral observation always agrees
with what conventional metadata (getprop/dumpsys/pm) already implies — i.e.
the probe never surfaces information that is inconsistent with, more
specific than, or absent from metadata — that supports H0. This would be a
complete, successful experiment, not a failed one.

BASELINE:
For each assumption tested, the conventional-metadata answer is recorded
first (Section 5 per-probe entries below), before the behavioral probe is
run, so the comparison is not written after the fact.

WHAT WOULD CHANGE MY MIND (stated in advance):
- Toward H1: any probe run where the behavioral observation is PASS/FAIL in
  a way conventional metadata could not have predicted (metadata says
  "should work" but probe observes FAIL, or vice versa), reproduced at
  R1 or higher.
- Toward H0: probe observations that track metadata 1:1 across repeated
  runs and environments, with no case of divergence, would weaken H1 and
  should be reported plainly as such rather than reframed as a tooling
  problem.

5. PROBE SELECTION AND JUSTIFICATION
================================================================================

The brief allows "up to 3" probes. Two are proposed here, not three — a
third pure-adb, no-companion-APK candidate that was meaningfully distinct
(rather than a near-duplicate of probe 1) was not found; padding to three
with a weaker or dependency-heavier probe would violate the "MUST NOT
force-fit" and minimalism rules more than it would satisfy the brief.
Rejected candidates are logged below with reasoning (Section 9, Confounder
rule / honesty-over-volume).

--------------------------------------------------------------------------
PROBE 1 — provisional name: probe_storage_write
--------------------------------------------------------------------------
ASSUMPTION UNDER TEST: "A file can be written to and read back from a
fixed, legacy-style external-storage path on this device/emulator, via
adb shell, right now."

Why this assumption: scoped storage (Android 10+) is one of the most
common real-world Android compatibility failure classes — code written
against pre-scoped-storage assumptions silently breaks, and the actual
enforcement varies by OEM, API level, and even per-app compatibility
shims. It is a compatibility failure class in the ordinary sense the
hypothesis is about.

BASELINE (metadata claim, recorded before probing):
  `adb shell getprop ro.build.version.sdk` states the API level, from
  which conventional wisdom infers whether scoped storage "should" be
  enforced. This is a prediction from metadata, not an observation.

PROBE (behavioral):
  `adb shell` — write a small marker file to a fixed path (e.g.
  /sdcard/pulse_probe_test), read it back, delete it. All via plain shell
  commands, no companion app.

OBSERVATION mapping:
  PASS — write+read-back succeeded and content matched.
  FAIL — write or read-back failed, or content mismatched.
  UNKNOWN — adb itself failed/timed out for a reason unrelated to the
    write (e.g. device offline) — must not be coded as FAIL.

RESEARCH LOG (per template Section "RESEARCH LOG (per probe...)"):
  What does this establish? Whether this specific path is actually
    writable/readable right now, on this specific device/emulator/OS
    build — a direct behavioral fact.
  What does it NOT establish? Whether the SAME result holds for a real
    installed app's own sandboxed storage calls (this probe uses the shell
    user's own permissions, not an app's runtime-granted permission state)
    — it establishes an environment-level fact, not an app-level one. This
    limitation must be stated plainly wherever probe 1's results are used.
  Alternative explanations for a FAIL: read-only filesystem mount state,
    full disk, SELinux policy blocking shell writes specifically (distinct
    from blocking app writes), adb running as a restricted (non-root)
    shell user on this build.
  False-positive risk: low — a PASS is a direct, unambiguous observation.
  False-negative risk: a transient FAIL (disk momentarily full, adb
    connection hiccup) could be mistaken for a genuine compatibility FAIL
    if not reproduced — mitigated by the reproducibility ladder (Section
    7) rather than by trusting a single run.
  Would UNKNOWN be more honest in some cases? Yes — any adb-transport-level
    error must map to UNKNOWN, never silently to FAIL.
  Does it modify device state? Yes, transiently — writes one small file,
    which the probe itself deletes as its last step. Documented here per
    Section 9's requirement to record this explicitly.
  Independently reproducible? Yes — no external state, no prior setup
    beyond an attached device/emulator.

Novelty-firewall re-check for this probe specifically: resembles no
existing certified/solved system (scoped-storage compliance is normally
checked by manually reading platform docs or trial-and-error in-app, not
by a standalone reusable probe) — proceeding is justified.

--------------------------------------------------------------------------
PROBE 2 — provisional name: probe_settings_persist
--------------------------------------------------------------------------
ASSUMPTION UNDER TEST: "A value written to the Android Settings provider
via adb shell persists unchanged when read back immediately after."

Why this assumption: aggressive OEM battery/RAM-management layers (common
on several non-stock Android skins) are known to silently revert or
override settings-provider writes as part of background "optimization"
behavior — a real compatibility failure class distinct from probe 1's
storage-permission class, and one where the divergence between "declared"
and "actual" state is not visible from static metadata inspection at all
(there is no metadata flag that says "this OEM layer will revert your
write").

BASELINE (metadata claim, recorded before probing):
  None meaningfully exists — this is the specific case the brief calls out
  as "entirely absent from conventional metadata," not just a case of
  imprecise metadata. That absence is itself recorded as the baseline.

PROBE (behavioral):
  `adb shell settings put global pulse_probe_test_key <value>` followed
  immediately by `adb shell settings get global pulse_probe_test_key`.
  Uses an inert, custom, non-functional key name in the `global`
  namespace — chosen specifically so the write has no effect on any real
  OS behavior (nothing reads this key), keeping the probe non-destructive
  while still testing whether the settings-provider write/read path itself
  is available and honest on this environment. The probe deletes the key
  (`settings delete global pulse_probe_test_key`) as its last step.

OBSERVATION mapping:
  PASS — value read back matches what was written.
  FAIL — value differs or key is absent on read-back.
  UNKNOWN — the `settings put`/`get` command itself errored (e.g.
    permission denied at the shell level) rather than silently
    succeeding/failing on content.

RESEARCH LOG:
  What does this establish? Whether the settings-provider write path is
    reachable and honest, right now, from an adb shell context, on this
    device/emulator/OS build.
  What does it NOT establish? Whether an installed app (running with its
    own, more restricted, non-shell UID) would see the same persistence
    behavior — same environment-vs-app-level caveat as probe 1.
  Alternative explanations for a FAIL: SELinux/MDM policy blocking
    `settings put` for shell specifically, a race between write and
    read-back (unlikely given they run sequentially, but recorded as a
    theoretical confounder), an OEM layer actively reverting third-party
    global-namespace writes even for inert keys.
  False-positive risk: low, same reasoning as probe 1.
  False-negative risk: same class as probe 1 — a transient shell error
    must map to UNKNOWN, not FAIL.
  Would UNKNOWN be more honest in some cases? Yes, same rule as probe 1.
  Does it modify device state? Yes, transiently — writes one inert,
    non-functional key to the global settings namespace, deleted by the
    probe's last step. No real OS behavior reads or is affected by this
    key.
  Independently reproducible? Yes.

Novelty-firewall re-check for this probe specifically: OEM settings-revert
behavior is widely anecdotally known (e.g. in the context of notification
delivery on aggressive-battery-management OEM skins) but not, as far as
checked here, packaged as a reusable, falsifiable, comparison-over-time
probe anywhere — proceeding is justified.

REJECTED CANDIDATES (considered, not selected)
--------------------------------------------------------------------------
- background_service_runs — explicitly named in the brief itself as
  heavily confounded by OEM/Doze/process-lifecycle behavior. Not selected,
  per the brief's own instruction that this is a poor fit for experiment
  001.
- Clipboard background-read restriction (Android 10+) — genuinely
  interesting (behavior with literally no corresponding metadata flag,
  even stronger a case than probe 2), but reliably observing it requires a
  companion test APK exercising ClipboardManager from an actual
  foreground/background app context — plain `adb shell` cannot query
  clipboard state on its own. Rejected for this experiment to keep
  dependencies at stdlib + adb wrapper only per the entropy budget;
  worth flagging as a strong candidate for a future experiment that
  explicitly budgets for a minimal test APK.
- Package-visibility (Android 11+ `<queries>` manifest restrictions) —
  same problem as clipboard: `adb shell pm list packages` runs with full
  shell-level visibility regardless of app-level query restrictions, so it
  cannot actually exercise the assumption without a companion APK.
  Rejected for the same reason.
- Cleartext/HTTP network-policy behavior — explicitly out of scope per the
  brief ("Network calls from Pulse itself: 0 ... skip network-availability
  probes in experiment 001"). Not considered further.

8. FALSIFICATION REPORT (Section 13 deliverable)
================================================================================

QUESTION:
Do behavioral probes for storage-write and settings-provider-persist
assumptions surface anything beyond what conventional metadata already
implies, on this device?

ASSUMPTIONS TESTED:
  - storage_write: a file can be written to and read back from
    /sdcard/pulse_probe_test via adb shell.
  - settings_persist: a value written to a custom key in the `global`
    settings namespace via adb shell persists on immediate read-back.

BASELINE (recorded in Section 5/per-probe sections above, before
running):
  - storage_write: metadata (API level 36) predicts scoped storage is
    fully enforced; conventional wisdom offers a prediction, not an
    observation, about whether this specific legacy-style path would
    still be writable.
  - settings_persist: no metadata baseline exists at all for whether an
    OEM layer silently reverts a settings-provider write — this is the
    "entirely absent from conventional metadata" case named in advance.

OBSERVED RESULT (actual, from live runs against the Samsung Galaxy A53,
Android 16/API 36, R1/R2; the Google emulator, Android 14/API 34, R3; and
the Samsung Galaxy A54, Android 16/API 36, R4; recorded above):
  - storage_write: PASS (write+read-back matched) on every normal run
    across all three devices; correctly FAILs when pointed at an
    unwritable path, on all three.
  - settings_persist: PASS (put+get matched) on every run across all
    three devices; correctly FAILs when reading a never-written key, on
    all three (FAIL-detection case only exercised live from R2 onward).

NOVEL INFORMATION BEYOND BASELINE:
  - storage_write: the behavioral result (PASS) is MORE SPECIFIC than the
    metadata-only prediction -- API level alone does not tell you whether
    this exact path is writable right now on this exact device; the probe
    does. On this device/build, the API-level-36 "should be restricted"
    inference was not contradicted, but the probe is what actually
    confirmed the specific path's live state rather than assuming it.
  - settings_persist: the behavioral result (PASS) is information that
    was ENTIRELY ABSENT from any available metadata, exactly the strong
    case named in advance -- there is no OS-exposed flag stating whether
    this OEM's settings layer honors third-party writes to custom global
    keys. The probe is the only way this was known.

CONFOUNDERS CONSIDERED:
  - Three device identities tested: Samsung One UI/Android 16 physical
    device (A53, R1/R2); Google reference "google_apis" emulator/
    Android 14 (R3); Samsung One UI/Android 16 physical device, second
    model (A54, R4). This covers cross-build, cross-API-level, and
    same-OEM-different-model generality, but R4 does NOT add a second
    vendor's shipped OEM skin -- it is the same OEM as R1/R2. A
    different-vendor *physical* device would still add real evidence
    beyond what R3+R4 cover here; not claimed as already covered.
  - adb shell runs as the `shell` UID, not an installed app's sandboxed
    UID -- both probes establish an environment-level fact, not proof
    that an installed app's runtime-permission-gated calls would behave
    identically (stated as a limitation in each probe's research log,
    Section 5). This applies identically on the emulator and on both
    physical devices.
  - All runs on a given device happened within a few minutes of each
    other, same network/host, same device-awake state -- no evidence yet
    on behavior across a reboot, a Doze/idle cycle, or a different time
    of day, on any device.
  - Probe-implementation-error risk: mitigated for FAIL-detection on both
    probes as of R2, and reconfirmed at R3 (emulator) and R4 (second
    Samsung device) -- storage_write's deliberate FAIL case (unwritable
    path) and settings_persist's deliberate FAIL case (read a never-
    written key) both correctly returned FAIL on all three devices.
  - `pulse_history.json`'s single-record-per-assumption storage means its
    own "comparison" field is not itself cross-device evidence (see the
    R3 caveat in Section 7) -- the FACTs above are drawn from the direct
    pytest/pulse-run PASS/FAIL outputs, not from that comparison field.

REPRODUCIBILITY LEVEL ACHIEVED: R4 for both probes, both PASS and FAIL
  detection paths, across three device identities (see Section 7). The
  different-OEM-physical-device gap is unaffected by R4 (see below).
